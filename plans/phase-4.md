# Phase 4: A real marketplace develops

## Objective
Accounts with different material interests autonomously negotiate and settle—or visibly abandon—real bargains.

## Implementation
- Depends on phases 1/3. Add controller-owned trade submission/session-bound packet uptake in `src/bots/runtime.rs`/`src/bots/social.rs`, reusing `src/world/trade.rs` and `src/server.rs` persistence; never impersonate QA controllers.
- Add a bounded interest-driven market policy in `src/bots/pursuits.rs`: own holdings, use/future-character wants and available capacity determine whether to advertise, propose, counteroffer, accept or refuse. Evaluate received advertised/offered goods against those interests; unsuitable terms lead to a justified counteroffer or refusal, not automatic exchange. Bound negotiation/expiry and stop on incompatible wants or unavailable means; no universal price table or scripted item/quantity sequence.
- Extend `src/bots/dialogue.rs`'s no-trading prompt, `Intent`/reply schema and allowed-intent validation for those market actions; language interprets/expresses policy-supported terms, never supplies consent or assets by itself. Integrate incoming market messages with `Brain::receive`/runtime uptake rather than leaving only travel/follow handling. Replace blanket private/guild and bot-profile exclusions for this path with recipient-aware routing: local advertisements, tells addressed to this account and delivered guild chat may inform its policy; sender echoes, unrelated addressed offers and system notices cannot accept bargains. Preserve existing adventure validation and language budgets/failure rules.
- Private/guild TEXT has speaker ID `-1`; resolve its name only against legitimately observed account identity, not hidden Directory state. An unknown name can supply an advertisement, not binding consent; observe/revalidate the counterparty before agreement/exchange. Bind each side's explicit consent to that account and the identical current terms/version: goods/quantities each way, installment order/balance, rendezvous and expiry. Counteroffers or changed terms invalidate prior acceptance; vague assent, forged text, stale sessions and another actor's acceptance cannot authorize a trade. Expose only communicated offers and own assessments, never the other's hidden wants/stock.
- In pursuits/`src/store.rs`, retain account-bound consent, negotiated goods/price, rendezvous, confirmed installments, balance and expiry/refusal/default resolution across banking/restart/death. Reserve promised stock; revalidate each character/session/revision. Commit installment progress atomically with inventory exchange, or bind it to an equivalent durable transaction identity; replay cannot pay twice. No event-sourcing system, invented escrow/currency/enforcement.
- Reuse `Directory::chat` in `src/world/chat.rs` for public/private/guild conversation with real audiences/membership. No recipient mind-reading; unsupported cross-server meetings/language failures end explicitly.

## Verification
- Common contract: red–green `community_market_` cases cover suitable/unsuitable offers, partial/final delivery, capacity, changed/reserved stock, refusal/departure/expiry, death/restart, failed writes and stale/duplicate receipts. Crash after exchange commit but before mind update must recover the same settlement without repaying; holdings/revision alone cannot prove payment. Preserve human-input guards.
- Under the common contract's existing protected game testing API/native bridge, prepare only legitimate initial holdings/interests, communication/reach and capacity. Actual controllers must traverse holdings/interests → received advertisement/offer → unsuitable-offer rejection or counteroffer → both sides' agreement to identical terms → bank/rendezvous → committed partial/final installments or explicit abandonment with remaining balance. No test-authored agreement, direct policy invocation, post-setup steering or trade-API-only substitute. Trace each received message, recipient/observed identity, interest-based decision, terms version/consent and committed exchange. Include reconnect and departure; vary wants/items/quantities/locations so a changed interest changes the response, not a seventeen-Life script.
- Require controller-level private and guild cases: an intended recipient/member understands a received offer, changes market state and replies or acts accordingly; sender echoes, another recipient's offer, nonmembers, unknown identity and stale/changed-term acceptance cannot create consent. Include bot-to-bot bargaining formerly blocked by the profile filter. Delivery/rendering alone fails this gate.
- Normal-client trade UI supports inspection/accept/refusal; show consequential advertisement, disagreement, banking/rendezvous and settled holdings or visible abandonment, including properly scoped private/guild replies. Pair frames with message→decision→consent→commit traces, not chatter alone. This is C07/C08's wanted-goods bargaining and honored multi-trip exchange, not a functioning trade API mistaken for an autonomous marketplace.
